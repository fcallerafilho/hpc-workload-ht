At a glance

What is cross-validation (and what are these “time-aware splitters”)?

To choose a model's settings we must estimate how well it will do on data it hasn't seen — without touching the final test set. Cross-validation (CV) does this by splitting the training data into a few folds: train on some, check on the held-out fold, rotate, average. We keep the setting that scores best.

When does this happen in our project? Only inside Pass 2 (the grid search). Pass 1 trains each model once and tests once — no CV. In Pass 2, the grid search splits the training set into folds to decide which hyperparameters are best, then refits the winner and scores it on the test set. The final test set is never part of the CV (it's a later, separate set of jobs), so it stays honest — which is exactly how we can see the leak: CV claimed 0.46, the test delivered 0.08.

The catch for us. Our rows are overlapping 10-minute windows of the same job (each shares 39 of its 40 snapshots with the next). A random split drops near-identical windows of one job on both sides — the model effectively sees the answer, so the CV score is fake-high. Pass 2 trusted that inflated score and picked over-complex models → the regression.

The fix is better ways to split — note these are splitting rules, not models (the models stay LightGBM / CatBoost / HGB):

  • GroupKFold — put every window of a given job entirely on one side, so the overlap can't leak.
  • TimeSeriesSplit / PurgedKFold — split by time: train on the past, validate on the future (with a small gap so nothing bleeds across) — exactly how the model is used in deployment.

Section 2 below measures how much each splitter “cheats”, and section 3 shows the twist: grouping alone isn't enough — the split must respect time.

1 · The exact baseline

Why the baseline is the failure rate. A random (constant) classifier has, at every recall, a precision equal to the share of positives among all rows — so its precision–recall curve is a flat line at y = prevalence, and its average precision (PR-AUC) equals the positive prevalence. Any real model must clear that bar to be worth anything.

Because PR-AUC is scored on the test windows, the baseline is the fraction of positive test windows = 0.0403. Concretely: the Dummy predicts the train prior 0.0320 (its mean_proba), but the score it achieves — its pr_auc = 0.0403 — is the test prevalence. That is the baseline, so the best model is ×1.97 it, not the ×2.5 the train prior would suggest. ROC-AUC baseline = 0.5.

What counts as a “positive”? Three things are easy to confuse — only the last is the target:

  • Job state (COMPLETED / TIMEOUT / FAILED / OOM / NODE_FAIL) — used only for the per-state breakdown.
  • Snapshot label (0/1 per 15-s snapshot: is it in the 2 h before a failure job's end?) — an intermediate step.
  • Window label (0/1 per 40-snapshot window, by majority vote: ≥20 of 40 snapshots positive) — this is what the model predicts and is scored on.

So a positive = a window in the final 2 h of a job that ultimately failed, not “any window of a failed job” and not a snapshot. That is why a long TIMEOUT job is only ~10% positive windows (just its tail), while short OOM jobs are ~99% positive. The baseline counts positive windows, matching the unit the model predicts.

3 · Why temporal validation is required

Selecting boosting rounds, a leak-free same-period monitor points to ~260 rounds — exactly where the future/test score is worst. A temporal monitor points to ~120 rounds — the test peak. Grouping removes same-job leakage but not temporal over-optimism.

7 · Bottom line

Fixing CV was the win: it removes the Pass-2 regression and makes selection trustworthy; the corrected 0.0403 baseline makes the numbers honestly interpretable. Temporal validation — not merely grouping — is the decisive point. A large jump beyond ~0.088 will need pipeline/feature changes, deliberately left for a later session.
