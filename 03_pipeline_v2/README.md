# pipeline_v2 — Session 3

Proactive failure prediction for GPU nodes, rebuilt from scratch.

Nothing here imports from `benchmark/` (Session 1) or `cv_strategies/` (Session 2), and no array either of
them produced is read. Their *numbers* are quoted for comparison; their code and artifacts are not touched.
What did carry over — deliberately, and unchanged — are the time notions Session 2 established:

1. Prediction is **per window**, never per job. The dataset is never collapsed to one row per job.
2. Labels are **time-based**: a snapshot is positive iff its job ends in a failure state *and* the snapshot
   falls within `HORIZON_H` hours of that end. A window takes the majority vote of its snapshots.
3. The train/test split is **temporal**, by job end date. Never random.
4. Selection uses a **temporal holdout** and **purged, expanding-window CV**. Shuffled or merely grouped CV
   is never used to select anything.
5. Every window carries its own end timestamp, so any split, fold or embargo is expressed in time.

## Result

| | PR-AUC | random baseline | lift |
|---|---|---|---|
| Session 1 (best of ~15 classifiers) | 0.0795 | 0.0403 | 1.97× |
| Session 2 (honest CV + tuning) | 0.0860 | 0.0403 | 2.13× |
| **Session 3** | **0.1253** | 0.0402 | **3.12×** |

95 % cluster-bootstrap interval over test *jobs*: **[2.35×, 4.30×]**. The same test population as the
earlier sessions — same 80/20 job split by end date, every test window kept — so the baselines agree and
the comparison is legitimate.

Three things belong next to that number every time it is quoted:

- **It is "about 3×", not a precise multiple.** The same configuration fitted on 85 % of train scores
  0.1382 (3.44×), and a paired bootstrap cannot separate the two (−0.0097, 95 % CI [−0.0258, +0.0114]).
  Notebooks 03–05 use that 85 %-train protocol throughout, which is why they quote 3.44×; notebook 06
  reports the pre-registered full-train refit. Neither is the "real" one — they are two draws from the same
  pipeline.
- **Most of the skill is on TIMEOUT.** TIMEOUT is 70 % of the positives and is usually a user
  under-estimating walltime, not a sick node. Restricted to genuine hardware failures the result falls to
  **1.94×**.
- **Coverage, not accuracy, is the binding constraint.** Of 1,158 test jobs that failed, only 378 (33 %)
  lasted long enough to produce a single 20-minute window. 293 were alerted — **25 % of all failures** — at
  a 50 % false-alarm rate on completed jobs.

## The two transferable findings

**Measuring more of the node is what paid.** Going from 8 metrics to 36 is worth +0.059 PR-AUC on its own —
essentially the whole improvement. Converting cumulative counters to per-second rates adds +0.006. Nothing
else helped: trajectory columns (`delta`, `slope`) carry under 1 % of model gain, per-node normalisation and
node identity both scored *below* the plain expanded set.

**Four purged folds can reject, but they cannot choose.** Of twenty challengers, four were resolvably worse
than the incumbent — so the folds are not blind — but *none* was resolvably better. Obeying the
cross-validated argmax anyway cost 30.7 % of PR-AUC, and notebook 04 takes the failure apart: the argmax's
columns were harmless (−0.6 %); its deeper trees made early stopping halt at 26 rounds instead of ~150
(−27.4 %), and matched-round refits show only a quarter of that loss is tree depth itself. The temporal
holdout that early stopping watches barely registered it, because the holdout is adjacent in time while the
test set is further away.

## Running it

```bash
python -c "import pv2; pv2.build_scaffold()"       # once, ~1 min
jupyter lab notebooks/                             # then run 01 → 06 in order
```

Every expensive step caches to `results/*.json` or `artifacts/`, so re-running a notebook is cheap and
resumable. The three datasets (`primary` at W=40, `w10`, `w20`) total ~10.5 GB on disk; each takes a few
minutes to build. Peak RSS stays near 3.5 GB — the matrices are memory-mapped and materialised in chunks,
because the machine this was developed on has ~7 GB free.

## Configuration of the reported model

| | |
|---|---|
| columns | rung C — 36 metrics × `min max mean std` = 144 |
| model | LightGBM, module defaults (31 leaves, lr 0.05, `min_child_samples` 100) |
| rounds | 141, pre-registered from the holdout-stopped fit of the same configuration |
| window | 40 snapshots = 20 min, rejected if it contains a gap > 60 s |
| horizon | 2 h |
| label | majority — ≥ 20 of the 40 snapshots inside the horizon |
| positives | FAILED, TIMEOUT, OUT_OF_MEMORY, NODE_FAIL |

## Operating point

The F2 threshold chosen on the holdout flags 28 % of windows at 0.070 precision — recall-heavy and not, on
its own, an operable setting. The alert-budget view is the useful one: **the top 0.1 % of windows are 90 %
true positives** (22.4× precision lift). A small high-purity queue is the shape this model should be
deployed in, not a threshold that flags a quarter of the cluster.

Rank and alert with raw scores. An isotonic map fitted on the holdout takes Brier from 0.2278 to 0.0466 but
costs 12.7 % of PR-AUC, because it collapses score ranges into ties — calibrate only where a probability is
actually read.

## Not comparable with Skrzeczek

That thesis reports ROC-AUC ≈ 0.98 on the same public trace by aggregating each job's entire time series
into one row and then classifying it — the features include the failure. This work predicts from a
20-minute window that ends *before* a 2-hour horizon opens. Different question, different unit, different
metric. The two numbers should never be placed side by side.

## What a next session should attack

1. **Coverage.** Most failing jobs die before a 20-minute window exists. Notebook 05's window sweep is the
   first look (W=10 covers 50 % of failing jobs instead of 33 %); a variable-length or ragged-window design
   is the real answer.
2. **Separate node health from user error.** A two-headed model predicting hardware failure and walltime
   overrun separately would be more useful — and more honest — than one that pools them.
3. **A denser train stride.** The learning curve is still rising at stride 5: the last doubling of training
   windows bought +6.5 % of PR-AUC. This is the one clearly untested lever, and it costs compute rather
   than credibility.
4. **Intervals everywhere.** Several comparisons in Sessions 1–2 are smaller than the bootstrap interval
   measured here.
